# 残留 Pi 会话

本文记录一件事：终端关闭后，容器 `pi_yolo_env` 里的 `pi` 进程不会退出。

本文包含已实测的事实、本期决定，以及将来若要做时已经设计好的方案。

记录时的仓库状态：`/home/jones/app/cyolo`，分支 `main`，HEAD `d7d0f84`。记录日期 2026-10-13。

## 0. 决定（本期）

**不做任何机制改动。先靠使用纪律：收工前在 `pi` 里按 Ctrl+D 或输入 `/exit`。**

理由：属于 YAGNI。现有证据只支持"知道正确退出方式后能避免"，不支持为此改入口、加会话标记、改现有测试。

重新考虑的触发条件，出现任一条即重开：

1. 容器里再次出现无人可连的 `pi` 残留，尤其导致 `cyolo pi --build` 被拒绝。
2. 残留累积到明显占内存，例如同时 ≥3 个，或合计 ≥1 GB。
3. 出现一次非本人主动操作导致的中断：SSH 断线、终端崩溃、会话被强杀。

触发后按代价从低到高做，够用就停：

1. **逃生通道**：`cyolo clean`（列出并清理残留），并改掉 `--build` 的误导文案。
2. **方案 A**：会话标记 + 下一次启动时回收。设计见第 3 节。

## 1. 现象与证据

2026-10-13 实测，宿主 WSL 实例 `Ubuntu-H`，容器 `pi_yolo_env`：

| 项目 | 实测值 |
| --- | --- |
| 容器内 `pi` 进程 | 11 个 |
| 合计内存（RSS） | 约 3.4 GB |
| 最老的进程 | 存活 5 天 |
| 打开的 socket | 每个进程均为 0，即没有在请求模型 |
| 宿主侧 `docker exec` 客户端进程 | 0 个 |
| 容器内读 `/dev/pts/*` | 全部阻塞，说明 pty 主端仍被打开 |

用户当时的认知是"已经全部退掉了"。残留会在无感知的情况下持续产生。

### 1.1 链路与根因

一次会话由四环组成：

| 环 | 内容 | 关闭终端窗口后 |
| --- | --- | --- |
| 1 | Windows Terminal 窗口 | 消失 |
| 2 | WSL 里的 shell 与 `docker exec` 客户端进程 | 消失 |
| 3 | Docker 守护进程为这次 exec 分配的 pty 对 | **仍在** |
| 4 | 容器里的 `pi`，其 stdin/stdout 是该 pty 的从端 | **仍在** |

内核只在第 4 环那对 pty 的主端关闭时，才给前台进程发 SIGHUP。主端由第 3 环持有，所以信号永远不发。

`pi` 本身的处理是正确的：`dist/modes/interactive/interactive-mode.js:3581` 注册 SIGHUP/SIGTERM，收到后走优雅退出，并在 `:3502` 调用 `exit(0)`。问题是没人给它发信号。

结论：`docker exec` 不把客户端连接与容器内进程的生命周期绑定。这不是配置错误，是它的既定行为。

### 1.2 拒绝构建的逻辑

- `bin/cyolo:93` `check_update_allowed()`：容器处于运行状态时执行 `scripts/check_pi_processes.py`。
- `scripts/check_pi_processes.py`：扫描容器 `/proc`，只要命令行首个词是 `pi` 就输出 `busy`。
- `bin/cyolo:102`：收到 `busy` 时报错退出。

该文案把残留误说成"还有一个没退的会话"（"退出所有容器 Pi 会话后执行"）。用户按字面做了，但仍然被拒。

### 1.3 复现实验

用一次性容器（`cyolo-pi:latest`，实验后已 `docker rm -f`）验证机制可行性：

| 问题 | 结果 |
| --- | --- |
| `docker exec` 客户端是否继承并持有额外的 fd | 是，客户端 fd 9 指向给定文件 |
| 客户端被 `kill -9` 后，内核是否释放该 fd 上的 `flock` | 是，立即释放 |
| 该 fd 是否被转发进容器（若是，标记永不释放） | 否，容器内进程的 fd 中不存在 |
| 客户端 `kill -9` 后，容器内被 exec 的进程是否随之退出 | 否，`-i` 下同样残留 |
| 容器内 `/tmp` 与宿主 `/tmp` 是否同一份 | 是，compose 映射 `/tmp:/tmp`，uid 一致 |

## 2. 术语

- **客户端进程**：宿主上的 `docker exec` 进程，由用户的终端管着。
- **会话记录**：`cyolo` 启动 `pi` 之前写下的小文件，一次会话一份。
- **锁**：加在会话记录上的 `flock`，由客户端进程持有。
- **残留**：客户端进程已死、但容器里的 `pi` 仍活着的会话。

## 3. 方案 A（本期不实现）

### 3.1 步骤

1. `cyolo` 在共享 `/tmp` 下建目录 `cyolo-sessions/<会话 ID>/`，内含 `lock` 与 `pid` 两个文件。
2. `cyolo` 打开 `lock` 并 `flock -n`，然后 `exec docker exec`。客户端进程继承该锁。
3. 容器里用一个 shell 包装：先把 `$$` 写入 `pid`，再 `exec pi`，PID 不变。`/tmp` 双向共享，宿主可读。
   - 实现备选：不改命令行，改用 `--env CYOLO_SESSION=<ID>` 传递标记，回收时按标记扫描容器 `/proc/*/environ` 找到 PID。这样"参数原样传递"的现有测试不受影响。
4. 用户关闭终端后，客户端进程死，内核自动放锁；容器里的 `pi` 留下。
5. 下一次 `cyolo` 启动时逐条检查记录：`flock` 能拿到，说明原客户端已死，是残留；拿不到，说明仍在使用，不动。

判据只有这一条。不猜时间、内存或 socket。

### 3.2 清理规则

| 情况 | 锁 | 动作 |
| --- | --- | --- |
| 终端仍开着 | 被持有 | 不动 |
| 终端已关、`pi` 仍在 | 空闲 | 杀掉记录中的 PID，删记录 |
| 正常退出（Ctrl+D、`/exit`） | 空闲 | 无进程可杀，只删记录 |
| 容器被重建，记录的容器 ID 或启动时间不匹配 | 任意 | 什么都不杀，只删记录 |
| 记录中的 PID 已不存在 | 空闲 | 只删记录 |
| 记录损坏、读不出 PID | 任意 | 只删记录 |

第四行是防误杀的关键：容器重建后 PID 会被复用，对不上的记录一律不动作。

### 3.3 已定的取舍

| 决策点 | 结论 |
| --- | --- |
| 目标不变式 | 会话随终端消失而结束，不做 tmux 之类的可重连会话 |
| 覆盖情形 | 只保证：关终端窗口、SSH 断线、`kill -9` 客户端。不负责：`wsl --shutdown`、宿主重启、Docker 守护进程重启、睡眠唤醒 |
| 清理范围 | 只杀本次会话的 `pi`；判断不确定时宁可残留 |
| 误杀偏好 | 宁可残留，不可误杀 |
| 回收时机 | 下一次 `cyolo` 启动时，不引入常驻进程 |
| 记录位置 | 共享 `/tmp/cyolo-sessions/`，宿主重启即自然失效，无需过期策略 |
| `--build` 遇到残留 | 先回收可证明为孤儿的会话，再构建；活跃会话仍然拒绝 |
| 用户可见性 | 静默；仅在确实回收了东西时打印一行 |

不负责的四项中，`wsl --shutdown` 与守护进程重启会连容器进程一起带走，宿主重启同理，睡眠唤醒不产生"终端消失"事件，因此都不需要额外机制。

### 3.4 验收标准

1. 开 3 个 cyolo 会话，分别用关窗口、`kill -9`、断开连接结束，容器里不再残留 `pi`。
2. 有活跃会话时，`cyolo pi --build` 仍然拒绝。
3. 现有测试全绿（`python3 -m unittest discover -s tests`），新增测试覆盖第 1、2 条。

## 4. 已否决的替代方案

- **容器内 tmux / abduco**：会话可重连，但内存照占、`--build` 照样被拒；还要改镜像、安装 tmux，并与 `pi` 的 TUI 键位和键盘协议冲突。收益不抵成本。
- **常驻看门狗、立即回收**：判据相同，只把时机提前；代价是新增一个宿主常驻进程和它自己的失败面。残留的代价只是内存，不值这个复杂度。
- **只改 `--build` 的报错文案**：能减少误导，但不解决问题。可并入"逃生通道"，见第 0 节的触发条件。

## 5. 维护说明

- 会话记录放在 `/tmp`，不写进仓库、不写进配置、不需要定期清理。宿主重启后自然失效。
- 该机制对用户不可见：日常使用不需要额外操作。

## 6. 相邻但不在范围内

- MCP 子进程可能比 `pi` 会话活得更久。2026-10-13 实测到一个 `notify_hub` 进程在会话结束后独自存活约 21 小时。它不属于本文范围。
